# Long方格真实窗口恢复准入与收口阶段审计

> 审计日期：2026-08-06
>
> 范围：真实窗口恢复准入、复合事务缺口、产品自有窗口边界、Phase 0/MVP 收口计数
>
> 结论：准入合同已建立但当前明确阻断；本阶段不连接窗口批处理适配器

## 1. 收口还剩多少阶段

以“桌面管理 MVP 的首条布局恢复垂直链”为范围，在本阶段开始时还有 **4 个工程阶段**；本阶段完成后剩余 **3 个工程阶段**：

| 阶段 | 状态 | 交付与出口 |
| --- | --- | --- |
| A. 真实窗口提交准入合同 | 本阶段完成 | 绑定计划、配置、revision、拓扑、撤销、窗口所有权和人工证据的有限阻断结果；App 零接线 |
| B. 产品自有窗口注册与只读 DesktopHost 桥 | 待开发 | 只注册 Long方格创建的容器窗口；稳定容器 ID、进程/线程所有权、代次和 Bounds 只读快照；不移动窗口 |
| C. 配置与窗口复合事务 | 待开发 | 单次确认绑定配置与窗口计划；捕获、应用、复读、配置/窗口双向补偿、失败可恢复、一次性撤销协同 |
| D. RC 硬化与交付收口 | 待开发/待证据 | 干净会话 UIA、输入/显示/故障矩阵、关闭竞态、性能预算、一键打包与发布候选审计 |

这 4 阶段不包含任务栏美化、小组件/Long助手插件兼容和广泛第三方窗口特效；这些属于 MVP 后续能力，不应为了“看起来接近收口”混入当前安全关键链路。

## 2. 仍有 4 个外部证据门禁

GitHub `Phase 0 Exit` milestone 当前仍有 4 个开放 Issue：

- #19：I19-01–I19-10 真实输入、Narrator 与系统表面矩阵；
- #20：I20-01–I20-08 动态显示、DPI、旋转、电源/RDP/会话矩阵；
- #23：P1–P5 五人无提示可用性测试；
- #24：专用卷持久化边界和生产配置收口。

它们与工程阶段部分并行，但不能用源码合同或 CI 代替真实人工、硬件和专用环境证据。因而“还剩 3 个工程阶段”不等于“再合 3 个 PR 就可以发布”。

## 3. 为什么现在不能直接连接现有窗口事务

现有 `LayoutRecoveryTransactionCoordinator` 已覆盖窗口原位置捕获、批量应用、逐窗复读、显示 generation 陈旧检查和补偿回滚，是可靠的纯 Core/探针基础；但它的请求目前只绑定 generation、plan 和布尔审批，尚未绑定产品配置指纹、共享 edit revision、配置撤销令牌或一次性操作身份。

同时，通用 `ILayoutRecoveryWindowBatchAdapter` 只接受容器 ID 与 Bounds，没有产品级证据证明 HWND 由 Long方格当前 DesktopHost 创建和拥有。若 App 在配置保存后直接调用窗口事务，窗口失败或 App 退出可能形成“配置已经更新、窗口仍在旧位置”的分裂状态；当前一次性撤销只补偿配置，不能替代配置+窗口复合事务。

因此，本阶段不创建适配器实例、不把准入令牌送入 App、不枚举或移动真实 HWND。

## 4. 新的有限准入合同

`ProductWorkspaceRealWindowRecoveryAdmission` 使用默认阻断的 Flags 结果，一次返回全部缺口。绑定计划令牌包含：

- 权威当前拓扑 generation；
- 共享 edit revision；
- 当前正式配置 SHA-256 指纹；
- 规范化恢复计划 SHA-256 指纹；
- 已绑定的显式用户批准。

最终 Ready 还必须同时满足：配置级一次性撤销与计划令牌一致；计划未 Blocked；注册窗口集合与计划容器集合完全一致且无重复；窗口所有权已证明；复合事务与批处理适配器可用；回滚故障、输入/系统表面、动态显示和干净会话 UIA 证据全部通过。

任何 plan、configuration、topology generation 或 edit revision 变化都会形成有限 blocker。计划指纹使用有长度前缀、固定顺序和 InvariantCulture 数字格式的规范化输入，避免列表顺序或分隔符歧义。

## 5. 自动化与需求对齐证据

定向测试覆盖：全部证据成立时 Ready；当前产品状态多项阻断；拓扑/revision/配置/撤销/窗口集合同时陈旧；计划篡改与人工矩阵缺失；未批准、Blocked 和畸形计划拒绝。UI 源码合同继续要求 App 不引用真实窗口准入令牌、`LayoutRecoveryTransactionCoordinator` 或 `ILayoutRecoveryWindowBatchAdapter`。

本阶段只增加 Core 准入合同和文档，不新增 UI 按钮，因此 AutomationId 仍为 118。当前全量测试为 410/410；CI 等价覆盖率为行 92.04%（10910/11854）、分支 82.86%（2920/3524），通过仓库 90%/75% 门槛；Debug/Release 构建零警告零错误。启动链、单实例合同、Issue #19/#20/#23/#24 `ValidateOnly`、配置持久化和漏洞门禁通过；DesktopHost、文件操作安全与缩略图隔离按既有限制返回 `Conditional Pass`。真实 UIA 复跑时 PID 39208 仍响应正常但 `MainWindowHandle=0`，`FindFirst` 返回 `0x8000FFFF (E_UNEXPECTED)`，因此为环境 `Inconclusive`，不计作产品通过或失败。远端 CI 在发布流程中继续复核。

## 6. 下一阶段 B 的明确范围

下一阶段只建立“产品自有窗口注册与只读 DesktopHost 桥”：

1. 注册表只能接受 Long方格自己创建的容器窗口句柄；
2. 每条记录绑定容器 ID、DesktopHost 实例/线程、窗口代次和最后复读 Bounds；
3. 窗口销毁、句柄复用、DesktopHost 重启和重复容器必须有限拒绝；
4. App 只读取匿名计数和有限状态，不获得 HWND；
5. 仍不调用 SetWindowPos/DeferWindowPos，不改变 Z 序、激活、Region、UIA 或桌面文件。

只有阶段 B 的所有权与生命周期证据通过，阶段 C 才能设计复合提交，不允许绕过准入评估器直接连接现有探针适配器。
