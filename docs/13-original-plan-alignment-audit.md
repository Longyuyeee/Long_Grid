# Long Grid 初始计划对齐与偏移审计

审计日期：2026-08-02

初始基线：`8a93904`（2026-07-30 的 PRD、架构和路线图）

当前基线：`main` / `75f7e52`（合并 PR #61 后）

证据范围：`docs/02-product-requirements.md`、`docs/03-architecture.md`、`docs/04-roadmap.md`、当前源码/测试/探针、Phase 0 Exit Issue #19–#24、PR 与 CI

## 1. 执行摘要

结论：**产品方向没有偏移，开发顺序发生了显著偏移。**

本地优先、默认不移动文件、使用公开 Windows API、不注入 Explorer、先验证高风险系统边界再产品化，这些初始原则一直保持。偏移发生在执行配比：自动化技术探针不断向更深的显示事务、配置故障和缩略图隔离矩阵扩展，而初始 Phase 0 同等要求的低保真体验原型、5 人可用性测试、负责人产品决策和真实硬件矩阵仍未开始或未完成。

这不是功能方向跑偏，也不是已进入 P1/P2 的范围蔓延；它属于**风险先行策略的失衡执行**。已有技术工作显著降低了未知风险，但继续扩展相邻格式或故障组合的边际收益已经低于关闭体验、决策和实机证据的收益。

当前仍不满足正式 MVP 开工门槛。纠偏重点不是推翻探针成果，而是冻结已充分举证的技术族扩展，优先完成最初计划中被延后的产品/体验和人工证据，并消除 Phase 0 与首个产品切片之间的循环门槛。

## 4. 偏移分类

### 4.1 没有发生的偏移

- 没有改变“10 秒内让混乱桌面变得清晰、可恢复”的产品愿景；
- 没有放弃本地优先、零惊吓、默认安全引用和可撤销原则；
- 没有把任务栏替换、插件生态、云同步或 Folder Portal 偷渡进 MVP；
- 没有采用 Explorer 注入、内核驱动或未文档化桌面嵌入作为正式路线。

### 4.2 已发生的偏移

1. **优先级偏移**：P0-03、P0-06、P0-07 的自动化深度持续增加，P0 体验轨和负责人决策没有同步推进。
2. **证据结构偏移**：E1/E2 的隔离探针证据丰富，但真实用户、真实输入、真实显示硬件证据不足。
3. **阶段节奏偏移**：六个退出 Issue 全部打开，Phase 0 缺少明确的技术探针停止规则，存在永久验证期风险。
4. **架构落地延迟**：不是架构方向改变，而是 Phase 0 延长导致最初规划的生产模块一直没有开始。
5. **门槛循环**：正式渲染表面、应用关闭和单实例接线依赖生产项目；若要求它们在创建生产项目之前全部完成，就无法退出 Phase 0。

偏移严重度：**中等，必须纠偏，但无需返工现有技术基础。**

## 5. 纠偏后的推进顺序

### R1：先关闭产品与体验不确定性（Issue #23）

- 负责人确认许可证、首版仅安全引用、Folder Portal 不进入首个切片、最低系统/架构/安装渠道和性能预算；
- 完成首次整理、引用/移动、撤销/恢复的可点击或可操作低保真流程；
- 执行至少 5 人无提示测试并记录误解点和严重度。

理由：这些是初始 Phase 0 的明确交付，并直接决定哪些技术兼容矩阵真正需要支持。没有产品范围，继续扩展格式和环境矩阵无法判断投入是否必要。

### R2：完成交互与系统表面人工矩阵（Issue #19）

使用现有可见交互宿主完成键鼠、触控、拖放、Narrator、Win+D、全屏、Alt+Tab、任务视图和 Explorer 重启。任何场景没有原始证据时保持 `Pending/Inconclusive`。

### R3：完成动态显示真实硬件矩阵（Issue #20）

在受控设备执行 DPI、旋转、热插拔、投影、睡眠、RDP 和 `WM_DPICHANGED`。自动事件注入或静态快照不能代替硬件结果。

### R4：只补必要的安全与兼容缺口（Issue #21–#22）

- 完成撤销、跨卷、ACL/只读卷、云/网络/重解析点等已承诺场景；
- HEIC/AVIF、Office/PDF、第三方 provider、ARM64 只在 #23 确认首发支持后进入必需矩阵；
- 不再因相邻格式或新故障组合自动延长 Phase 0；
- 正式渲染表面接线移到第一个生产切片验收，不再作为创建生产宿主前的阻断项。

### R5：关闭 Phase 0 合同并作出 ADR 决策（Issue #24、ADR-0001）

- Phase 0 必须确认配置 schema、迁移/回滚、原子存储、安全恢复和生产模块边界；
- 真实卷只读/空间耗尽在专用环境可用时补证；
- 应用关闭排空、完整单实例激活属于首个 App 切片的进入后验收，不再形成循环依赖；
- 汇总 #19–#24 的必要证据，把 ADR-0001 更新为 `Accepted`、`Revised` 或 `Rejected`。

### R6：建立只读 MVP 垂直切片

按 Contracts → Infrastructure → DesktopHost → App 的依赖顺序，实现“只读桌面目录 + 一个视觉容器 + 持久化引用”。真实移动、自动规则执行和 Folder Portal 继续保持关闭。

## 6. 防止再次偏移的执行规则

1. 同时最多推进一个技术证据切片和一个体验/决策切片；没有可用人员或设备时，技术切片可以继续，但不得扩展已完成探针族的支持范围。
2. 每个新 PR 必须关联一个仍未满足的退出条件，并在 PR 中说明它如何改变 `Pending`、`Conditional Pass` 或 `Pass`。
3. 已有 Conditional Pass 的探针只允许因 CI 回归、安全缺陷、明确支持决策或现有退出场景失败而继续深化。
4. Office/PDF、更多 codec、第三方 provider 和 ARM64 等矩阵由支持范围驱动，不由“还能继续测”驱动。
5. 每次审计同时报告技术轨和体验轨；不再用提交数、测试数或覆盖率替代阶段出口。
6. 生产接线类验证必须标明是“Phase 0 决策前置”还是“Phase 1 首片验收”，避免互相等待。

## 7. 下一次审计的通过标准

下一次计划对齐审计至少应看到：

- #23 有负责人决策记录和低保真测试证据；
- #19 或 #20 至少一个完整矩阵得到可复读结果；
- #21–#22 没有新增未经支持范围批准的相邻矩阵；
- #24 的 Phase 0 合同项与首片集成项已分开跟踪；
- ADR-0001 已具备明确 Go/No-Go 所需的剩余证据清单；
- 第一个生产切片的范围仍保持只读、可恢复和默认不移动文件。

最终判定：**保持最初产品方向，立即调整执行顺序。先补产品/体验与真实环境证据，再做有明确支持决策的技术收口；消除循环门槛后进入只读 MVP 垂直切片。**
