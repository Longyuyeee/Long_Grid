# 批量选择操作栏与键盘可达性审计

> 日期：2026-08-10
> 范围：批量加入与同方格批量移除列表的有限选择、清除、键盘和辅助功能合同
> 安全边界：不新增业务权限；零桌面文件内容读取、写入、移动、删除或重命名

## 1. 需求对齐

此前两个批量切片已经具备 Ctrl/Shift 多选、1..256 上限、原子配置提交和整批一次撤销，但纯组合键路径不够直观，也不利于仅使用键盘或辅助技术的用户。本切片在两个列表旁增加共同操作栏：

- 未分组列表提供“选择前 256 项”和“清除选择”；
- 已加入列表在当前选择全部属于同一方格时提供“选择此方格前 256 项”和“清除选择”；
- 现有 Ctrl/Shift 多选继续保留，两种路径共享相同数量、同方格和 256 上限门禁。

这不是“全选无限项目”。选择范围始终有限且可预测；跨方格混合选择不会获得扩展或提交能力，引用改归属仍严格保持单选。

## 2. 交互与辅助功能合同

四个入口均使用 WinUI 标准 `Button`，进入正常 Tab 顺序，并继承 Enter/Space 激活语义；每个按钮具有稳定 `AutomationId` 和独立 `AutomationProperties.Name`。按钮只在动作可执行时启用：候选为空时不能选择，未建立同方格上下文时不能扩展，选择为空时不能清除。

选择发生后，可见状态和机器状态都更新实际数量。清除后两侧分别报告 `ResolvedReferenceBatchAddSelection:Count=0` 或 `ResolvedReferenceBatchRemovalSelection:Count=0`，并持续报告 `DesktopFilesChanged=False`。这让 Narrator/UIA 和自动化测试可以判断操作结果，而不依赖颜色、位置或路径信息。

## 3. 状态与安全边界

“选择前 256 项”只遍历当前 presentation 提供的有限候选；“选择此方格前 256 项”先从现有选择证明唯一方格，再仅选择该方格候选。两者都先清除旧选择，不合并未知范围，也不触发 reducer、保存控制器或磁盘写入。

真正的批量加入/移除仍由既有确认框、generation/revision、锁定状态、唯一性、1..256 上限、原子 reducer 和一次撤销合同保护。本切片没有开放跨方格批量改归属、真实桌面文件操作或 DesktopHost 窗口执行。

## 4. 自动化合同

新增 4 个 AutomationId，权威源码合同由 130 增至 134。`Test-LongGridUi.ps1` 同时检查按钮默认禁用、事件处理器、辅助功能名称、有限 `.Take(...)`、同方格范围、显式清除、零数量机器状态和 `DesktopFilesChanged=False`；`Test-LongGridCleanSession.ps1 -ValidateOnly` 同步验证 134-ID 编排与不越权终止外来进程的边界。

## 5. 验证结论

本地 Release 构建为 0 警告、0 错误；全量测试 544/544 通过。Stage 83 单份 Cobertura 为行 91.12%（8105/8894）、分支 80.14%（2293/2861），通过 90%/75% 门槛。134-ID UI 源码合同、干净会话 `ValidateOnly`、启动链、Issue #19/#20/#23/#24 会话编排、单实例合同和依赖漏洞门禁均通过。

DesktopHost 交互切片为 `Conditional Pass` 且确认 `DesktopFilesReadOrChanged=False`；100 次持久化及终止/ACL 注入矩阵全部通过；文件操作安全与缩略图隔离探针均为 `ConditionalPass` 且清理成功。缩略图探针的 provider 提取限制仍按既有产品回退边界保留，不由本 UI 切片扩大。内部 RC、PR CI 与 main CI 将在准确提交上继续复核。交互桌面 live UIA 因本机会话既有外来无窗口进程继续保持 `PendingCleanInteractiveSession`，不得以静态合同冒充真实人工证据。

## 6. 后续方向

配置级批量选择、提交和撤销链已经形成可发现、有限、可键盘访问的闭环。下一阶段优先执行批量操作可用性与 Narrator/高对比度人工矩阵，或在获得独立准入后接入可见 DesktopHost；任务栏美化、小组件/插件运行时、跨方格批量改归属和真实桌面文件整理仍属于后续独立范围。
