## 1. 审计发现与需求对齐

PF-002A 已能从桌面空状态创建首个“新方格”，但继续审计真实代码后确认两个产品缺口：

1. 桌面入口把名称固定为“新方格”，控制中心则直接采用输入名称，两条入口没有共同的默认值决策；
2. 原布局只使用 `existingContainerCount % 8`，第 9 个方格会回到第 1 个方格的完全相同位置。

这与 iTop Easy Desktop、Stardock Fences 的连续就地创建体验不一致，也不能满足 Stage 153 对稳定默认名称和连续 20 个方格不完全重叠的验收要求。本轮只解决创建默认值和提交前规划，不把尚未存在的桌面右键、键盘或绘制入口写成已完成。

## 2. 统一创建策略

新增 `ProductWorkspaceContainerCreationDefaults`，桌面空状态与控制中心的正式创建链均通过该策略生成名称和位置：

- 自动名称依次为“新方格”“新方格 2”……，按忽略大小写的已有名称集合填补第一个空缺；
- 控制中心显式名称先去除首尾空白，并拒绝空白、控制字符、超过 256 字符和忽略大小写后的重名；
- 容器总数达到 100 时返回 `LimitReached`，不构造半成品；
- 桌面请求必须命中当前权威显示拓扑中的目标显示器，否则失败关闭；
- 控制中心优先使用权威主显示器，无权威拓扑时保留 `display-unassigned` 安全回退；
- 默认尺寸为 360×240 DIP；工作区更小时按工作区边界收缩，不产生屏外尺寸；
- 位置从 32×48 DIP 开始，以 24 DIP、每行 8 个槽位级联，并显式避开目标显示器上位置和尺寸完全相同的既有方格；
- 策略只返回决策，不保存配置、不发布窗口、不读取或移动桌面文件。

容器 ID 继续使用 `container-{Guid:N}`，创建前再与当前容器 ID 做精确冲突复核。策略成功后仍只通过 `ProductWorkspaceCommitCoordinator.CommitContainer` 提交，成功文档再进入既有 session/read model/DesktopHost 投影链。

## 4. 失败与边界矩阵

| 输入/状态 | 决策 | 副作用 |
| --- | --- | --- |
| 已有名称包含“新方格”和“新方格 3” | 生成“新方格 2” | 仅返回规划 |
| 显式名称前后有 Unicode 空白 | 规范化后检查和提交 | 一次配置提交 |
| 空白、控制字符或超长名称 | `Invalid` | 零提交、零窗口 |
| 忽略大小写后重名 | `DuplicateName` | 零提交、零窗口 |
| 容器达到 100 | `LimitReached` | 零提交、零窗口 |
| 工作区或 DPI 非法 | `Invalid` | 零提交、零窗口 |
| 桌面请求显示器已消失/不再权威 | App 返回拒绝 | 零提交、零窗口 |
| 控制中心暂缺权威拓扑 | 使用有限未分配工作区默认值 | 保持原有可创建能力 |
| 既有槽位被占用 | 继续寻找下一个非完全重叠槽位 | 仅成功规划后提交 |
