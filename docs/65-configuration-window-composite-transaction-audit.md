# Long方格配置与产品窗口复合事务审计

> 审计日期：2026-08-06
>
> 范围：配置与产品窗口原子提交、代际绑定、复读验证、双向补偿、一次性撤销、App 安全边界
>
> 结论：工程阶段 C 的产品级复合事务合同完成；真实窗口适配器和 App 仍未接线，等待 RC/实机证据

## 1. 为什么不能直接串联已有提交

现有 `ProductWorkspaceCommitCoordinator` 在配置编辑进入异步保存控制器后即返回接受；已有 `LayoutRecoveryTransactionCoordinator` 独立捕获和恢复 Bounds。若先调用其中一个再调用另一个，第二步失败时无法证明第一步已经被同步补偿，可能形成“配置已更新、窗口仍在旧位置”或“窗口已移动、配置未持久化”的分裂状态。

本阶段新增 `ProductWorkspaceWindowCompositeTransactionCoordinator`，把两侧都抽象为可捕获、应用、复读、恢复和恢复复读的事务层。产品适配器必须提供真正的暂存/提交语义，不能把普通异步排队结果伪装成复合事务成功。

## 2. 绑定令牌

复合令牌同时绑定：

- 唯一 operation ID；
- 当前显示拓扑 generation；
- 变更前、成功后、撤销后的 edit revision；
- 窗口注册表 generation；
- DesktopHost 实例 ID 与宿主 generation；
- 变更前、成功后、撤销后的配置 SHA-256 指纹；
- 规范化布局计划 SHA-256 指纹；
- 已显式完成的 review approval。

签发前必须证明：配置前后均可投影；配置确实发生变化；计划未 Blocked；计划、前后状态和已验证注册表具有完全相同且无重复的容器集合；窗口所有权已证明；所有 generation、实例 ID 和 operation ID 均有效。任意状态、计划、容器集合或所有权变化都会使重新计算的令牌不同，并在关闭输入前有限拒绝。

## 3. 应用顺序和补偿

执行顺序固定为：

1. 复核完整请求和变更前 binding；
2. 关闭受影响产品窗口的输入；
3. 捕获配置快照，再捕获精确容器集合的窗口快照；
4. 再次复核所有 generation/指纹；
5. 应用窗口计划并立即复读；
6. 确认 binding 未变化后应用配置暂存结果并复读；
7. 对窗口和配置执行最终交叉复读；
8. 重新开启输入；
9. 只有全部成功才发布一次性复合撤销令牌。

窗口失败时只恢复已触碰的窗口层；配置开始应用后失败则先恢复配置、再恢复窗口，符合应用顺序的逆序补偿。每个恢复步骤都必须复读，且最终 binding 必须回到变更前状态。输入无法重新开启、恢复失败、恢复复读失败或 binding 无法回归时，事务进入 `RollbackFailed`，保持输入关闭并调用 `HideAffectedHosts`；隐藏失败另有 `EmergencyHideFailed`，不得继续展示不可信窗口。

异常只被转换为有限失败，不得越过补偿路径。协调器使用串行锁，同一旧 binding 的并发请求最多一个可以成功，后续请求有限返回 `Superseded`。

## 4. 一次性复合撤销

成功事务保留配置和精确容器窗口的原始快照，并签发只覆盖该 operation、成功 binding、撤销 binding 和计划指纹的撤销令牌。撤销必须满足：令牌完全一致、显式确认、当前 binding 仍等于成功 binding。

撤销前再次捕获当前成功状态作为前滚快照。若恢复原配置/窗口的任一步失败，协调器尝试把窗口与配置前滚回成功状态并复读：

- 前滚成功返回 `RolledForward`，原撤销令牌保留，可在问题排除后重试；
- 前滚失败返回 `RecoveryFailed`，隐藏窗口并清除不再可信的撤销令牌；
- 撤销完全成功后清除并释放令牌与全部快照，重复使用返回 `Unavailable`。

撤销不接受其他 operation、已变化的配置、edit revision、注册表 generation、DesktopHost 重启或拓扑变化。

## 5. 隐私与窗口边界

复合事务位于 Core，仅处理产品状态、容器 ID、有限 binding 和像素矩形；文件中不包含 `nint`、HWND 或任何 Win32 窗口写入 API。未来窗口层只能在 Infrastructure 内从阶段 B 的 verified 注册记录解析句柄，Core、App、计划和 UI 不得携带句柄。

本阶段没有把协调器、令牌或窗口适配器接入 App；没有调用 `SetWindowPos`、`DeferWindowPos`，没有改变 Z 序、激活、Region、UIA、Explorer、任务栏、注册表或桌面文件。源码合同继续强制 App 零引用，因此当前产品仍不会执行真实窗口恢复。

## 6. 自动化与需求对齐

定向测试覆盖：完整令牌、成功顺序、缺少确认、binding 陈旧、计划/容器篡改、窗口失败、配置失败、最终交叉漂移、捕获失败、输入关闭/开启失败、恢复失败与紧急隐藏、并发串行化、成功撤销、错误/未确认/陈旧撤销、撤销失败前滚以及前滚失败隐藏。

`eng/Test-LongGridUi.ps1 -ContractOnly` 要求复合合同包含拓扑、配置、注册表、DesktopHost、计划、所有权、补偿和单次撤销证据；同时禁止 Core 出现句柄/窗口写入 API，并禁止 App 引用复合事务。

| 最初需求 | 本阶段对齐结果 |
| --- | --- |
| 桌面文件整理 | 不扩权；复合事务不读写桌面文件 |
| 分组容器与布局恢复 | 建立配置与产品容器窗口不可分割的提交/撤销安全链 |
| 任务栏美化 | 未进入当前安全关键路径，保持 MVP 后续 |
| 自定义窗口效果 | 未启用 Region、合成、激活或第三方窗口控制 |
| 小组件/Long助手插件 | LPWP 协议不变；运行时继续等待 MVP 后续隔离实现 |

本地完整结果为 440/440 测试通过；覆盖率为行 91.03%（12284/13494）、分支 80.92%（3308/4088），通过仓库 90%/75% 门槛；Debug/Release `-warnaserror` 均为零警告零错误，格式、118-ID UI 源码合同、单实例合同和依赖漏洞门禁通过。DesktopHost 交互探针仍为 `Conditional Pass`；#19、#20、#23、#24 的 ValidateOnly 分别保持 `PendingManualEvidence`、`ResultsPending` 或 `PendingDedicatedEnvironmentEvidence`。没有创建真实产品容器、移动窗口或伪造外部证据；远端 CI 在 PR 发布后复核。

## 7. 还剩多少阶段

以桌面管理 MVP 首条布局恢复垂直链为范围，本阶段后只剩 **1 个工程阶段：RC 硬化与交付收口**。它至少包括：

1. Infrastructure 内部的 verified-window batch adapter 与产品配置暂存适配器；
2. 完整回滚故障矩阵、输入/系统表面矩阵、动态显示矩阵和关闭竞态；
3. 干净会话 118-ID UIA 与真实产品容器验收；
4. 性能、资源、恢复、安装、升级、卸载、一键启动和一键打包审计；
5. 满足准入评估器全部 blocker 后，才决定是否把真实执行入口接入 App。

“剩 1 个工程阶段”不代表只剩一个 PR，也不包含任务栏美化、小组件/插件运行时和广泛窗口特效。GitHub #19、#20、#23、#24 仍是并行但不可跳过的真实人工、硬件和专用环境证据门禁。
