# Stage 102：连续保存修订准入与 CI 确定性审计

日期：2026-08-12

基线：`main` / `5915e76`（PR #152 已合入）

触发证据：main CI run `31513109786` 中 `RealStoreReloadsContainerEditsWithoutChangingReferencedFile` 唯一失败；期望 `XDip=104`，实际复读 `0`，其余 632 项通过。同一提交的 PR CI 与本地测试通过，判定为调度相关竞态，而不是布局 reducer、projector 或 Store 数据合同错误。

结论：**旧保存修订的工作流提交入口已关闭；确定性逆序恢复测试、原失败用例、全量 Release 与覆盖率门禁通过；最终状态仍以 PR CI 和合并后的 main CI 为准。**

## 1. 根因与影响

`ProductWorkspaceSaveController` 在防抖结束后把修订标记为 `Saving`，随后主动让出一次执行权，再调用 `ProductConfigurationSaveWorkflow.SaveAsync`。这产生了一个过去未被状态机覆盖的间隙：

1. 修订 1 已经通过防抖并成为当时的活跃保存；
2. 它在调用工作流前让出执行权；
3. 修订 2 被接受、通过防抖并先进入 latest-wins 保存协调器；
4. 修订 1 随后恢复并成为最后一次入队文档。

旧完成结果虽然不会覆盖产品状态，但旧文档仍可能按工作流调用顺序成为最终持久化内容。因此原有“latest-result”保护不足以证明“latest-document”持久化语义。

## 2. 修复合同

Core 状态机新增 `CanSubmitSave(snapshot, revision)`，普通保存只有同时满足以下条件才能调用工作流：

- 状态为 `Saving`；
- 活动为普通 `Save`，不是 `Retry`；
- `CurrentRevision` 等于待提交修订；
- `ActiveSaveRevision` 等于待提交修订。

Infrastructure 在让出执行权后、工作流调用前重新取得该准入。工作流调用本身再由控制器内的窄提交信号量排序：若旧修订先取得准入，它一定先完成工作流调用，新修订随后入队；若新修订已经成为权威修订，旧修订直接退出且永不进入工作流。信号量只覆盖准入与 `SaveAsync` 调用，不覆盖底层异步落盘等待，避免不必要地串行化 I/O。

重试继续走独立的 `RetryAsync` 合同，不能借用普通保存准入。关闭仍等待所有已接受操作；安全完成后才释放完成门和提交门。

## 3. 确定性回归

`IProductWorkspaceSaveScheduler` 增加可替换的 `YieldAsync` 调度点。生产实现保持真实异步让出；测试实现可以精确控制两个修订恢复顺序。

新增回归固定执行：修订 1 先进入保存让出点，修订 2 后进入但先恢复并保存，最后才恢复修订 1。断言工作流只收到一个名称为 `Second` 的文档且 `SavedRevision=2`。该测试不依赖线程池繁忙程度、毫秒窗口或重复运行碰撞。

状态机测试另行证明等待中的旧修订、被新修订替代的活跃修订以及 Retry 活动均不能取得普通保存准入。

本修复直接支撑桌面方格重命名、位置、外观、折叠、锁定和引用编辑的连续保存可靠性，符合“稳定、快速、零惊吓”和关闭不丢最新编辑的最初需求。它不新增 UI、AutomationId、配置字段、桌面文件写入/移动、Catalog 探测、DesktopHost 窗口执行、任务栏修改或插件权限。

当前主目标仍是 Phase 0/内部 RC 收尾与 #19/#20/#23/#24 外部证据。任务栏美化、小组件/Long助手插件运行时和广泛窗口特效仍属于后续获批阶段；本次 CI 修复不改变路线图优先级，也不把内部产物提升为可公开分发。
