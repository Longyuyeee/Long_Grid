## 1. 审计目的与判定口径

本次不是继续增加功能，而是冻结当前最先进分支，重新回答三个问题：

1. 代码是否仍在实现最初约定的 Long方格，而不是偏成控制中心、测试工具或其他 Windows 工具；
2. 桌面整理、任务栏美化、自有窗口效果、现代 UI、启动/打包、Widgets 与 Long助手兼容等初始需求实际完成到哪里；
3. 当前测试是否证明了用户预期效果，而不只是脚本自身合同通过。

判定以 [产品需求基线](02-product-requirements.md)、[竞品审计](01-competitive-analysis.md)、[任务栏与窗口能力审计](06-desktop-taskbar-audit.md)、[小组件兼容设计](07-widget-plugin-compatibility.md)、[交互设计](09-interaction-design-audit.md)和 [Stage 153 功能总计划](153-product-feature-parity-development-plan.md)为准。Core 类型、测试桩或文档存在不等于用户功能完成；只有正式 App/DesktopHost 可发现、可操作、可恢复并取得对应真实证据，才可记为产品完成。

## 2. 执行摘要

### 2.1 没有发生根本产品方向偏移

- 正式实现仍坚持本地优先、安全引用、不擅自移动/删除桌面文件；
- 没有 Explorer 注入、任务栏替换、内核驱动或常驻轮询；
- 工程仍围绕桌面方格、引用、布局、恢复、DesktopHost、UIA 和有限 Shell 操作推进；
- WinUI 3 正式 App、桌面产品 Surface、现代窗口材质、统一启动和内部 RC 打包链均已存在。

因此项目没有偏成文件搬运器、Explorer 外壳替代品或单纯原型。

### 2.2 发生了明显的“收口与交付偏移”

- 30 个 PF 项仍为 **0 Complete**；PF-001～PF-005 只是 `EngineeringComplete / ProductEvidencePending`，PF-006 仍在开发；
- 主要工程深度集中在安全状态机、控制中心和证据链，用户最直观的桌面直接操作、自动整理、快速隐藏、托盘/全局快捷键、命名快照仍未形成 MVP 闭环；
- Stage 文档已经到 196，但基本产品完成项仍为 0，说明切片与证据粒度过细，产品结果收敛不足；
- 当前功能分支领先 `origin/main` 37 个提交、落后 0 个提交，约增加 27,162 行并删除 542 行。真实实现量很大，但长期不集成主分支已构成回归、交接和合并风险；
- README、视觉需求、品牌资产审计和 Stage 153 的部分“当前事实”已落后于代码。

### 2.3 当前不能宣称 MVP、Beta 或竞品对标完成

已有界面和可运行能力，但离 iTop Easy Desktop 的低摩擦整理闭环、Fences 的桌面直接操作成熟度仍有明显差距；任务栏美化与 Widgets/Long助手插件运行时尚未开始产品实现。当前准确阶段是：**产品功能逐项开发 / 工程预览 / 不可公开分发**。

Long方格的差异化仍成立：安全、可逆、本地、无注入和可扩展；但“安全工程深度”尚未转化为同等顺滑的端到端用户体验。

## 6. 偏移与风险清单

### P0：未发现安全方向偏移

没有证据显示产品跨越“不擅自移动文件、不注入 Explorer、不执行不受信插件”的红线。

### P1：产品性能目标与脚本合同脱节（Stage 198 已部分纠偏）

`Test-LongGridDesktopFirstStartup.ps1` 的合同字段全部通过：首次控制中心隐藏、唯一 DesktopHost、第二实例重定向、稳定期存活、退出无残留、临时配置零写入。本轮三次真实进程测量分别为 5107、1589、1140 ms。

Stage 198 复核确认该脚本测量独立进程冷启动，而 PF-001 的 1 秒条款针对已驻留 App 的运行期开启。现已为冷启动建立默认 10 秒硬门禁并证明强制 1 秒会正确失败；运行期开启 1 秒仍为专用真实证据 Pending。“脚本 Pass”仍不能替代尚未测量的产品目标 Pass。

### P1：产品完成度没有随切片数收敛

30 个 PF 项为 0 Complete，PF-001～005 的外部真人证据债务长期堆积。后续不得再以新增测试类或 Stage 数量代表产品进度，应优先关闭可见旅程和产品验收。

### P1：长期功能分支产生集成偏移

当前分支相对 `origin/main` 为 37 commits ahead / 0 behind。虽然没有落后主分支，但大批量未集成修改会增加最终合并、CI、交接和回滚成本。完成本审计后，应先通过 PR/主分支 CI 关闭集成风险，再开展新的大型切片。

### P1：iTop 核心旅程仍不完整

自动整理、快速隐藏/托盘/全局快捷键和低摩擦首次整理仍缺失。继续深挖外围细节而推迟这些能力，会形成竞品对标方向的实际偏移。

### P2：实现文件过度集中

当前 `App.xaml.cs` 约 3824 行、`MainWindow.xaml.cs` 约 4986 行、`MainWindow.xaml` 约 1840 行、桌面 Surface 与生命周期控制器分别约 3177/2530 行。Core/Infrastructure/App 分层仍在，但组合根、窗口和 Surface 过大，已经增加理解与回归成本。应在 PF-007/自动规则扩大写路径前提取命令协调、Presenter、设置和 Surface 输入/绘制边界。

### P2：任务栏需求发生优先级重分类

用户最初把任务栏美化、自定义窗口列为基本能力；正式 PRD 为了风险控制把任务栏改成 P1、默认关闭的实验模块。自有窗口效果已有部分实现，任务栏运行时为零。这个变化是合理的安全分期，但仍属于需求优先级变化，必须由产品路线明确记录，不能默认为已经对齐。

### P2：文档真相分散

仓库已有大量阶段审计，入口文档部分仍称“技术验证”“UI Shell 尚未建立”或“缩略图未消费”。本次已同步修正关键入口；以后以 PRD、交互设计、Stage 153 和最新全量审计为当前真相，旧 Stage 只保留历史证据。

## 7. 纠偏后的开发顺序

### Gate A：先关闭集成与基线风险

1. 将当前分支经 PR、完整 CI 和审阅集成到 `main`；
2. 把启动性能门从“只记录”提升为明确的 Expected/Actual/Difference 门禁，并定位冷启动/重复启动耗时；
3. 对 PF-001～PF-005 建立一次集中真人验收批次，关闭能关闭的物理输入、Narrator、高对比、文本缩放和截图证据。

### Gate B：完成桌面整理最小闭环

1. PF-006C1：PageUp/PageDown 跨视口导航；
2. PF-006C2：桌面框选与选择收敛；
3. PF-007：从桌面/Explorer 显式拖入安全引用，清楚区分“加入方格”和“移动文件”；
4. PF-011 + PF-020/PF-021：首次引导、规则建议/预览/冲突/撤销，形成 iTop 式低摩擦自动整理闭环；
5. PF-033 + PF-051：快速隐藏、托盘/全局快捷键和命名快照。

### Gate C：扩展竞品宽度与视觉收口

依次处理 Portal、Tabs/Roll-up/Peek、工作区、现代视觉/动效/无障碍、安装更新。任务栏仅按 [安全能力路线](06-desktop-taskbar-audit.md)实现默认关闭、可恢复的 P1 实验模块；Widgets/LPWP 运行时继续保持 P2，先做包发现、权限、签名、隔离 Host、配额和生命周期，不加载任意 DLL/脚本进入核心进程。

## 9. 最终结论

项目仍在正确产品方向上，且已有大量真实代码、正式 UI、DesktopHost、启动/打包与安全操作成果；问题不是“没有开发”，而是工程深度、文档数量和产品收口之间失衡。当前最重要的纠偏不是扩大任务栏或插件范围，而是先集成当前大分支、把真实性能纳入门禁、完成桌面直接整理与自动整理闭环，并集中关闭 PF-001～005 的产品证据债务。

在上述 Gate A/B 完成前，Long方格仍应标记为 **Engineering Preview / Not for Distribution**。
