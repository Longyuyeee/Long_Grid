# Stage 100：正式空工作区首个方格创建入口审计

日期：2026-08-11

范围：正式工作区原始空状态、创建编辑器对齐、焦点交互、UIA 与安全边界

结论：自动化范围通过；真实键盘、Narrator、缩放、触控和焦点可见性证据仍为 Pending

## 1. 需求与竞品交互对齐

原始需求要求桌面管理不仅能展示和筛选方格，还要让第一次创建路径清晰、现代且低认知负担。此前正式工作区在没有任何方格时只有说明文字，用户必须自行发现上方编辑器；这不符合 `docs/09-interaction-design-audit.md` 对空状态“提供明确主动作”的约束，也弱于 iTop Easy Desktop 一类产品在空白场景中直接引导下一步的做法。

本阶段补充“还没有正式方格”卡片与“开始创建第一个方格”按钮。按钮复用现有名称编辑器和现有“创建并保存”提交动作，不引入第二套创建流程。这样既缩短第一次操作路径，也保持 Long方格对显式提交、安全保存和桌面文件零修改的产品边界。

## 2. 准入策略

`ProductWorkspaceEmptyCreateShortcutPolicy` 只接收有限事实：

- 读模型是否明确代表空工作区；
- 正式读容器计数；
- 编辑器是否允许创建；
- 编辑候选计数。

仅当“明确空 + 读计数为 0 + 可创建 + 编辑候选为 0”同时成立时入口可用。负计数返回 `Invalid`；未加载、只读、已有容器或读写投影暂时不一致均返回 `Unavailable`。策略不读取名称、路径、持久化目标、Catalog、遥测或桌面身份。

`ProductWorkspaceReadPresentation` 新增 `IsKnownEmptyWorkspace`：未加载状态为 `false`，无保存配置和有效零容器快照为 `true`。App 在读模型刷新和编辑器刷新后都重新计算入口，防止会话转换时使用另一侧的陈旧状态。

## 3. 交互与安全边界

用户显式点击后只执行：

1. 再次解析准入策略，状态变化时拒绝；
2. 以 `FocusState.Programmatic` 聚焦现有 `ProductWorkspaceContainerNameEditor`；
3. 通过既有状态区域报告是否成功聚焦。

入口不会清空或填写名称，不会调用创建按钮处理器，不会提交或保存配置，也不会刷新 Catalog、移动/删除桌面文件或执行 DesktopHost。用户必须自行输入合法名称并再次明确点击“创建并保存”，因此创建仍沿用既有 revision、验证和保存控制器。

## 4. UIA 与验证

新增唯一 AutomationId：`ProductWorkspaceEmptyCreateButton`，权威 UI 合同由 140-ID 更新为 141-ID。初始状态固定为折叠、禁用和有限机器状态；可用、拒绝和聚焦结果均包含 `Focused`、`Changed=False` 与 `DesktopFilesChanged=False`。

自动化结果：

- Core 单元测试：624/624；
- 覆盖率：行 91.20%、分支 81.43%，通过 90%/75% 门禁；
- UI 源码合同：141-ID，通过；
- 空状态策略覆盖可用、未对齐和负计数失败关闭；
- 源码合同确认读/编辑双刷新、只聚焦现有编辑器且不接入创建、保存或桌面执行路径。

真实 720px、200% 文本缩放、键盘焦点可见性、Narrator 朗读、高对比度和触控仍须在专用无个人内容账户执行，不能由源码合同替代。

## 5. 后续方向

下一阶段继续按 Phase 0 收尾顺序推进，不扩大到任务栏美化、小组件/插件运行时或广泛窗口特效。优先选择仍能提高正式核心任务完成度、同时保持零桌面文件修改和可自动审计边界的有限交互切片；外部 #19/#20/#23/#24 与 BSA 人工证据仍是最终收口门禁。
