## 1. 本轮重新审计的准入边界

仓库已经具备正式 v1 schema、原子存储、latest-wins 入队、关闭排空、恢复、导入/导出和证据管理，但 App 中仍没有可编辑的真实产品状态聚合：

- 首次整理方格只记录名称与三个匿名引用，源码和界面均明确标记“仅内存”；
- 主题切换同样明确标记“仅内存”，当前 v1 schema 也没有应用主题字段；
- Core 目前提供只读桌面目录、身份、布局规划和正式配置合同，没有一个已经获准把真实 DesktopHost/目录状态投影为 `ProductConfigurationDocument` 的可编辑聚合；
- MainWindow 仍为零 `EnqueueAsync`，不会在启动、主题切换、匿名练习、恢复差异演示或关闭时伪造普通产品保存。

因此本轮不把演示方格、匿名项目、默认空白配置或主题选择冒充真实用户产品状态。本轮只准入真实状态源接入后必需、且可以独立验证的保存结果与显式重试合同。

## 2. 保存工作流合同

新增 `ProductConfigurationSaveWorkflow`，位于 UI 与既有 `ProductConfigurationSaveCoordinator` 之间。它保留 coordinator 的深快照、latest-wins、取消隔离和关闭排空语义，并把普通保存完成结果收敛为有限集合：

- `Saved`：已完成持久化；
- `Failed`：失败并只公开有限 `ProductConfigurationSaveError`；
- `NoRetryAvailable`：当前没有可重放的失败快照；
- `Completed`：关闭排空已经开始，拒绝新保存或重试。

无效 schema 在深快照入口即转换为 `InvalidConfiguration`，不会把内部合同异常、路径或原始 I/O 消息传给未来 UI。

## 3. 显式重试语义

工作流只保留最近一次、仍然是最新用户意图的可重试深快照：

- `DamagedEvidence`、`WriteLeaseUnavailable` 和 `IoFailure` 可在外部条件修复后显式重试；
- `InvalidConfiguration` 不保留重试，因为重放相同无效文档没有恢复价值；
- 新保存会取代旧失败快照，成功后不再允许重复重试；
- 重试再次失败时仍保持同一深快照；调用者后来修改原对象不会改变待重试内容；
- 调用者取消只取消等待，不撤销已经接收的保存，也不会产生含糊的重复重试入口；
- `CompleteAsync` 与保存接收使用同一把进程内门，避免“工作流已接收但 coordinator 已先完成”的竞态。

工作流不自动循环、不使用无界退避、不在后台自行覆盖损坏证据。损坏证据必须先通过现有恢复/重置流程处理，之后才能由用户或未来 UI 明确重试。

## 4. App 接线与零伪写入证明

App 现在持有 `ProductConfigurationSaveWorkflow`，关闭时通过它完成原有 5 秒有界排空。此接线把未来产品保存统一约束到有限结果与显式重试 API，但本切片没有向 MainWindow 注入保存委托，也没有新增任何普通产品状态入队调用。

该决定是需求对齐而不是功能缺失掩盖：真实保存必须等待“真实容器/引用状态聚合 → v1 配置投影 → UI 保存状态与重试入口”这一整条链同时落地。匿名原型在此之前继续保持可验证的零写入。

## 6. 下一条真实产品保存切片

下一切片必须同时交付以下能力，才可以首次从普通产品 UI 调用 `SaveAsync`：

1. 定义单一、可编辑且不依赖匿名演示控件的产品状态聚合；
2. 只从已解析的稳定桌面项目身份创建 `Reference`，不得从显示文字或临时列表索引反推目标；
3. 将真实容器外观和 DIP/显示器放置投影为当前 v1 文档，并通过 Core validator；
4. 首次保存、后续变更和删除使用同一快照来源，明确 debounce/latest-wins 边界；
5. UI 显示保存中、已保存、有限失败和可重试状态，并保持键盘/UIA/高对比合同；
6. 覆盖保存与关闭、第二实例激活、恢复/导入、显示变化及连续编辑竞态。

在这六项完成前，不把本切片描述为“自动保存已上线”。
